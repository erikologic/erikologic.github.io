## Concepts and key takeaways

_Note: most of these are from the course, sprinkled with some of my own knowledge as well!_

- **Model**: the thinking engine served by a model provider (OpenAI, Anthropic) or run locally.
- **Harness**: what connects a model to the environment, e.g. Claude Code, VS Code Copilot, or OpenCode. Harnesses usually provide a chat interface for a human to talk with the model, and tools that let a model interact with files, the web, MCPs, etc.
- **Agent**: a model + harness configuration.
- **Environment**: the outside world an agent interacts with, e.g. instructions such as AGENTS.md and skills; code self-documentation; and deterministic guardrails such as permissions, tests, and static typing.
- **Instructions**: non-deterministic prompts that harnesses automatically include in the context through standardised or proprietary processes. For example, all harnesses (apart from Claude Code) check for an [AGENTS.md](https://agents.md/) file at the project root (or even in subfolders), or know how to use an [Agent Skill](https://agentskills.io/). Adopting standards provides some interoperability, e.g. adapting an environment to different agent configurations or reusing [someone else's skill](https://vercel.com/marketplace).
- Where we have leverage to improve performance:
  - The **harness** has little influence. This is not directly a takeaway from the course; it comes from some extra academic research I read.
  - The **model** can provide drastically different results, although improvements diminish as costs increase.
  - The **environment** is where most of the quick wins are. The drawbacks are context pollution -> attention degradation and the need for good maintenance.
- **Model Non-determinism**: a feature (not a bug!) of LLMs. An LLM's internal sampler can be tuned. The author links to research arguing that there is an optimal threshold of randomness for LLMs, that it is not zero, and that going below it causes a steep decline in performance.
- **Turns**: whatever happens between user requests, including all model provider requests and tool calls/responses.  
- **Prompts**: the instructions that are sent to the model:
  - **System Prompt**: sent to the model at the beginning of a session to set the model's personality and role.
  - **User Prompt**: the instructions sent to the model at each interaction (including tool calls, etc.) to tell it what to do.
- **Context**: the information available to the model at a given time, generally the whole conversation history of your chatbot. The more we add, the more we pay and the greater the risk of context pollution.
- **Token**: the atomic unit of information processed by the model, representing a symbol (word, subword, punctuation, etc.) in numerical form.
- **Context Window**: the arbitrary maximum number of tokens that a model can process at once.
- **Session**: a sequence of Turns that share the same Context.  
- **Attention Relationships**: a quadratic pattern that affects all current models and is the main cause of Attention Degradation.
- **Smart Zone / Dumb Zone**: the parts of the Context Window in which the model performs best/worst. Pocock uses roughly 150k tokens as a rule-of-thumb boundary for where model performance starts to decline.  
  _I did some research into this myself, and even recent frontier models are affected. The course author's take is that the maximum context window is mainly a marketing gimmick._
- **Statelessness**: the model has no context between sessions, and there are strategies to mitigate this. The author's take is that this is a feature, that the environment should provide the minimum required state, and that memory systems are mostly context polluters.
- **Costs**:
  - Input tokens: the tokens that are sent to the model, including the prompt and the context (e.g. the whole conversation so far).
  - Output tokens: the tokens that are generated by the model.
  - Cached input tokens: each processed message is cached by the model provider for a certain amount of time. If the same message is sent again, it will be processed at a much lower cost than a fresh one. So, when we send the whole conversation again, we generally pay only for the latest message as input tokens, while the rest is cached. Note that caches expire after five minutes or one hour, depending on the provider and plan. For example, coming back to a conversation after a call could fall into uncached territory and trigger a full charge.
  - Cached output tokens: the same as above, but for output tokens. This could happen if the harness crashes but we manage to resume the conversation.
- **Cost per Task / Quality**: an interesting insight for model selection is understanding both how much it costs to fulfil a task and the final quality achieved. A less capable model might take more turns to complete a task, and tokenisation algorithms can differ between model classes. [DeepSWE](https://deepswe.datacurve.ai/) provides good comparisons for these metrics.
- **Hallucination**: one of the core problems with LLMs: confidently wrong model output.
  - **Factuality Hallucination**: the model is confident about a fact that is not true. This happens because of a lack of Parametric Knowledge (knowledge from the model's training data) and is also affected by the Knowledge Cutoff (when training data stopped being collected and processed). The cure is Contextual Knowledge: enriching the model with external knowledge, e.g. instructions, code, or search engine results.
  - **Faithfulness Hallucination**: can happen even when the model has all the required knowledge but is not using it correctly. Typically, it is an Attention Degradation problem, and the cure is to reduce the Context and operate in the Smart Zone.
- **Effort**: a dial that adjusts how much the model spends on "Reasoning" before returning an answer. The higher the effort, the more tokens are spent, increasing both cost and latency. Low effort is usually enough for simple mechanical tasks (e.g. few-shot refactors); maximum effort is mainly for benchmarking. The author's preference is Opus 4.8 at medium effort.  
  [DeepSWE](https://deepswe.datacurve.ai/) provides benchmarks for the various models and their effort levels:
  ![DeepSWE score benchmark chart](../../assets/deep-swe-score.webp)
- **N-shot prompting**: a technique for providing the model with N examples of the task we want it to perform, so that the model has an easier time predicting the right way to solve a particular task. It is particularly useful for "mechanical" tasks such as extensive refactoring to meet a new code standard.  
- **Subagents**: harnesses can spawn subagents to perform a task (e.g. search for information in the repo or on the web), so that the main agent's context is not polluted by the whole task but only by the final result. This task-delegation mechanism should be carefully balanced against the cost of spawning subagents. For example, Claude Code's default system prompt is 30k+ tokens, so it makes much more sense to spawn a subagent that needs to process 100k tokens than one that needs to process 10k!

## Working with Claude Code

The author provides a good overview of some useful commands and tricks to keep in mind when working with Claude Code:

- `/usage`: see your remaining allowance
- `/context`: visualise what's filling your context window
- `/clear`: start with a fresh context
- `Esc`: stop the agent mid-run
- Press `Esc` twice to rewind the conversation
- `@`: reference files
- `Ctrl+S`: stash
- Paste images
- `/ide`: install IDE extensions
- `/resume`: resume after a harness crash, for example
- `! npm run dev`: run a CLI command in the harness environment
- `Ctrl+Z`: freeze the TUI and return to the terminal; use `fg` to pull it back up
- Permissions: Claude Code has a permission system worth understanding, although nowadays auto mode (which asks an LLM to compare the user prompt with the command to be run) is usually trustworthy enough.

Regarding auto mode, there are ways to run code in a sandboxed environment, such as local dev containers or cloud VMs, with or without orchestration tools such as the author's [Sandcastle](https://github.com/mattpocock/sandcastle).

_Note: these commands are available in most harnesses._

## Fundamental techniques

### Reduce system prompt context usage

Much of the course content is centred on Context Management.

By default, Claude Code uses 30k+ tokens! Vanilla OpenCode currently sits at 6k. VS Code Copilot uses 16k.  

The author emphasises the need to develop the ability to inspect the system prompt and find a solution that suits your taste. This is particularly useful when using other harnesses.  
This can be done using harness tools (VS Code has a chat-debugging feature) or an HTTP proxy that intercepts and logs calls to disk.  

He also shares this configuration snippet to bring Claude Code's system prompt down to fewer than 20k tokens:

```json
{
  "permissions": {
    "deny": [
      "NotebookEdit",
      "DesignSync",
      "CronCreate",
      "CronDelete",
      "CronList",
      "EnterPlanMode",
      "ExitPlanMode",
      "PushNotification",
      "RemoteTrigger",
      "ReportFindings",
      "ScheduleWakeup",
      "AskUserQuestion"
    ]
  },
  "disableClaudeAiConnectors": true,
  "disableWorkflows": true,
  "disableBundledSkills": true,
  "disableArtifact": true
}
```

### Explore codebases

The author suggests spawning subagents to explore the codebase while staying inside the smart zone.
He doesn't propose creating "index" files (e.g. extensive Markdown files that explain the project's folder structure to agents) to avoid this exploration whenever taking on a task. He mentions in this course and elsewhere that his preference is for a self-explanatory codebase (with caveats) and avoiding duplicated information.

### `/teach` skill

The [/teach skill](https://www.aihero.dev/skills-teach) is the first one he introduces.  
The idea is to create a training tutorial for newcomers, for example, so that teaching can be tailored to the person's knowledge and interests, and onboarding is not a giant task to undertake.  

### Why plan mode is bad -> `/grill-me`

If we normally trigger an agent to implement a feature, it will rush to get to the end.  
If we use plan mode, it will most likely do the same, stopping a few steps earlier.  
That's because agents are trained to be sycophantic, providing an extremely agreeable counterpart so that humans are pulled into the interaction (notice those pull-in questions at the end of their responses?).  

The problem with this interaction is the lack of a "Design Concept" (_The Design of Design_ by F. P. Brooks Jr.): the concept floating around in the room, which everyone understands slightly differently and which sharpens as conversations develop.

To solve this, the author created the `/grill-with-docs` skill, which forces the model to ask questions until the design frontier has no further branches to explore.  

_Note: the author uses dictation heavily, which works really well, especially with Wispr Flow. I have tested it; it is great, though they charge $10/month. Some harnesses have internal dictation mode as well (Claude Code, VSC)._

### Compaction

When context grows towards the dumb zone, it's time to use techniques to reduce it.  

- `/clear`: Most of the time, clearing is the best strategy, especially at the end of one task and before starting another.
- `/compact`: Most harnesses provide `/compact`, which works well (especially if it accepts a prompt), though it has constraints, e.g. compacting within the same directory/harness. It is especially useful when transitioning from implementation -> QA. Avoid compacting halfway through resolving a task because it will degrade performance by creating a "secondary source" of information through the distillation that happens during compaction itself.
- `/handoff` skill: Another [skill from the author](https://www.aihero.dev/skills-handoff), useful when moving between agents, repos, machines, or colleagues. It creates a handoff document in a local file.
- `/subagent`: Perhaps not the best option when the context has grown too large, but some tasks are particularly well suited to running in a subagent with fresh context, e.g. a code review session that requires minimal task context and can report review comments back to the main session.
- Autocompaction: most harnesses trigger a compaction job at a configurable threshold. However, this is not the author's preferred method because of the high risk that it will happen halfway through resolving a task.

## Steering

Steering is the way to guide an agent's behaviour across different sessions.  

### Push vs Point

**Push**: always add information to the agent's initial context, e.g. via the system prompt, AGENTS.md, MCPs, etc.

**Point**: only add a thin reference in the initial context to where more information can be found, so the agent can decide whether to pull that context depending on the use case.

Pushed notions are always present in the agent's context (e.g. they are typically reloaded after compaction), but can contribute to attention degradation, to the point that the agent ignores those same rules.  
Pushed rules can also force the agent into overfitting, degrading performance. The author gives an example of PCI DSS rules causing an agent to warn about security risks when baking cakes.  

The author argues strongly against the practice of defaulting to push.

### Pointers

The author proposes his [/writing-for-agents skill](https://www.aihero.dev/skills-writing-for-agents) to produce agent-oriented documentation.  
He also strongly advocates for using pointers and provides this distinction:

- **Docs**: A thin reference from AGENTS.md to a file stored in the local repository.  
  Good for knowledge that is specific to a particular project in particular situations.
- **Navigation**: A reference from AGENTS.md to important parts of the codebase, to prevent the agent from scanning. A typical antipattern is loading too much into the context, including obvious information such as the various `npm run ...` commands or app routes in a Next.js application (agents can infer these from the files when needed, with minimal token waste).
- **Code Standards**: The author suggests extracting these into CODE_STANDARDS.md and adding a thin pointer in AGENTS.md.
- **Skills**: A standardised way to encapsulate knowledge. Harnesses know how to find and use skills installed locally or globally, importing their titles and descriptions into the context. Global skills can be reused across projects. Skills can be user-invoked only, in which case the harness will exclude them from the context.  
  Good for tasks/knowledge that span multiple repos, or for keeping knowledge hidden from the context but still available when a human prompts for it.

Consider also that most harnesses load nested AGENTS.md files when operating in subfolders, so locally relevant information can be encapsulated within that specific part of the project. _Claude Code, OpenCode V2, and VS Code (behind a configuration toggle) support this, but loading rules can vary; always check the harness documentation._  

### MCPs

From me...  
MCPs have historically wasted a huge number of tokens: every MCP action interface is exposed through verbose JSON, with some MCP servers exposing dozens of actions!  
The situation is good enough at the time of writing to consider them: harnesses such as Claude Code and VS Code implement lazy-loading techniques, while OpenCode V2 solves the problem with namespaces.  

### Pruning

The author emphasises the need to maintain a lean agent environment.  
Remember: adding instructions feels cheap; removing them requires maintenance and psychological effort (social anxiety, fear of breaking stuff).  

Some patterns:
- **Single-Source-of-Truth Issues**: The same notion is expressed in two different places. This carries costs in maintenance, context load, and prominence (reiterating the notion increases the model's focus on it). _I'd add the risk of the versions falling out of sync and confusing the model._ Solution: use thin pointers.  
- **Sediments**: Basically rot. Adding feels safe, removing feels risky. Project moves on, doc stays behind. _The usual stuff!_ Solution: default to not adding instructions and use thin pointers.  
- **No-ops**: An instruction that changes nothing about the model's output, e.g. "write a detailed commit message". Solution: remove it.  

Claude Code's `/init` command (which creates an initial CLAUDE.md file, equivalent to AGENTS.md) is a good playground for pruning skills because it creates a giant instruction with plenty of antipatterns, e.g.:

- `npm run` table -> the agent knows how to read package.json
- File list -> the agent knows how to call the `ls` tool
- Filler lines such as "This file provides guidance to the agent when working with code in this repository" -> yeah no s***! Just delete them
- Formatting conventions -> use deterministic tools such as Prettier and refer to its configuration
- Architecture reference -> provide a thin pointer if needed, but move that information towards the modules, e.g. JSDoc
- How to test this project -> move it into docs with a thin pointer, or into a skill

Trick! Trigger his skill with this prompt:

`/writing-for-agents I want you to find me candidates in AGENTS.md that have single-source-of-truth issues between AGENTS.md and the rest of the stuff on the filesystem. I want you to give me candidates for removal or for putting behind pointers. Basically, I want you to do a whole pruning pass on AGENTS.md, and the ideal state for it should be just a few navigation pointers to different documentation.`

### Automatic Memory

Most harnesses ship with a memory system, which can be accessed in Claude Code via `/memory`.  
The author's position is that this is more likely to do harm than good, and he recommends switching it off. A few reasons:

- as shown in the `/init` example, the agent is likely to include many antipatterns that will need to be pruned
- memory is managed by the agent, which decides when to prune and what to do with stored information; most likely, it will leave that information to rot
- memory is normally included in every session, causing context pollution -> attention degradation
- some stored information is specific to a workflow and does not need to be kept in context at all times

## Shipping

The author advocates for keeping sessions inside the model's smart zone.  
To do that, we need to split the journey:

- **Spec**: A document that describes where we are going.
- **Ticket**: A document that describes each individual leg.

The author advocates for GitHub Issues as a tracker and for letting the agent interact with the `gh` CLI. Any equivalent is fine, though.  
The `/setup-matt-pocock-skills` flow adds instructions to the repo after you confirm GitHub usage.  

**Workflow**:

- `/grill-with-docs` to discuss the feature in detail.
- [/to-spec](https://www.aihero.dev/skills-to-spec) in the same session to create the GitHub issue.  
  _This skill will ask for a test seam: "a place in the code where you can change behavior without editing the code at that point" (_Working Effectively with Legacy Code_ by Michael Feathers)._  
  _"Don't read the specs/tickets!" the author suggests._  
- [/to-tickets](https://www.aihero.dev/skills-to-tickets) to create the various subtasks in GitHub.  
  A few notes on splitting work into tickets:
  - Ideally, there is enough smart context left to create the tickets in the current session. The created spec is a great handoff document in case context needs to be reset.
  - Avoid slicing work horizontally (e.g. UI layer, application layer, database layer); instead, slice vertically using a "tracer bullet" approach (_The Pragmatic Programmer_ by Andrew Hunt and David Thomas): build a very thin end-to-end slice of a system early, so you can verify that the whole path actually works.
  - Aim for tickets that, by a finger-in-the-air assessment, can be executed inside a single session's smart zone, using Pocock's rough 150k-token reference.
  - Describe dependencies so that work can potentially be parallelised.
- Clear the context: `/clear` or restart Claude Code.
- [/implement](https://www.aihero.dev/skills-implement) with the issue link, which triggers the [/tdd](https://www.aihero.dev/skills-tdd) and [/code-review](https://www.aihero.dev/skills-code-review) skills. _Use auto mode!_
- `/tdd`:
  - Tautological tests: one common antipattern for LLMs is to create tests where the assertion recomputes the expected value the way the code does: `expect(add(a, b)).toBe(a + b)`.
  - The importance of feedback loops: where good feedback loops are present (unit tests, static typing), the results are much better than where they are difficult to achieve (UI).
- `/code-review` instantiates two subagents to perform two different parallel reviews:
  - Spec: has the issue faithfully been implemented?
  - Standards: does the code conform to standards?
- Manually QA the implementation.

**Spec-Driven Development**  
The author is not a fan of it. Code is the source of truth, and specs will eventually drift.  
He advocates archiving the spec/issue in GitHub and keeping it for auditing, but otherwise forgetting about it and keeping it out of the agent's regular reach (not in the codebase, where it could pollute context and confuse agents if it drifts).  

**Destination Change**  
What happens when a plan has to be modified?

- Close the outstanding tickets
- `/grill-with-docs` the spec and update it
- `/to-tickets` to generate the new ones
- `/implement` to continue

**`/goal`**  
Many harnesses implement a `/goal` command, which aims to pursue a goal in a single session until the goal is completed.  
The problem is that it extends work way inside the dumb zone and it relies on autocompaction.  

_My notes: this might be fixable by tweaking the maximum allowed context and automating workflow management/splitting. Also, the author hints at his other workflows that automate at least the ticket-creation part... BTW, tracer-bullet tickets are a good place to put a human in the loop, IMO._
